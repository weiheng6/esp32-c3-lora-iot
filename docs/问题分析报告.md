# 🔍 ESP32-C3 MQTT 上报卡死问题深度分析

## 问题描述
- **现象**：程序运行正常，MQTT 上报温湿度数据，但过一段时间自动停止上报
- **监视器表现**：整个系统卡死（没有新的日志输出）
- **已排除**：网络问题、MQTT 连接问题（已加重连机制）
- **结论**：固件层面的阻塞操作导致主循环卡住

---

## 🔴 根本原因分析

### **问题 1️⃣：WiFi.scanNetworks() 是超级阻塞操作** ⚠️ 最严重

**位置**：`src/web_server.cpp` 的 `handleScanWiFi()` 函数

```cpp
int n = WiFi.scanNetworks();  // ❌ 这会阻塞主线程 10-15 秒！
```

**为什么卡死**：
- 当用户在浏览器中点击"扫描 WiFi"按钮时，调用 handleScanWiFi()
- WiFi.scanNetworks() 是**阻塞式调用**，会 **独占 WiFi 硬件 10-15 秒**
- 主 loop 无法执行，导致：
  - ❌ MQTT loop 无法运行
  - ❌ 传感器采集停止
  - ❌ 看门狗定时器触发
  - ❌ 整个系统表现为"卡死"

### **问题 2️⃣：mqttCallback 中的 memcpy 可能触发阻塞** ⚠️ 中等

**位置**：`src/main.cpp` 的 `mqttCallback()` 函数

```cpp
memcpy(message, payload, length);  // ❌ 如果 payload 很大可能阻塞
```

**为什么卡死**：
- MQTT 回调处理时间过长
- 大的 JSON 解析可能消耗时间
- 虽然不如 scanNetworks 严重，但也会影响响应性

### **问题 3️⃣：loop 中的 delay(10) 太短** ⚠️ 轻微

**位置**：`src/main.cpp` 的 `loop()` 末尾

```cpp
delay(10);  // 只有 10ms，可能不够调度其他任务
```

**为什么可能卡死**：
- ESP32 需要执行其他系统任务（WiFi、蓝牙等）
- 10ms 太短，导致系统任务得不到足够执行时间
- 看门狗定时器可能触发重启

---

## 📊 问题优先级

| 问题 | 严重度 | 影响范围 | 修复优先级 |
|------|--------|---------|----------|
| WiFi.scanNetworks() 阻塞 | 🔴 致命 | 用户点击扫描按钮时 | 1️⃣ 最高 |
| MQTT callback 阻塞 | 🟡 中等 | 收到 MQTT 消息时 | 2️⃣ 高 |
| delay(10) 太短 | 🟢 轻微 | 持续存在 | 3️⃣ 中等 |

## ✅ 解决方案

### **方案 1：使用异步 WiFi 扫描**

**修改**：`src/web_server.cpp`

```cpp
// 原代码（阻塞式）：
int n = WiFi.scanNetworks();  // ❌ 阻塞 10-15 秒

// 新代码（异步非阻塞）：
int n = WiFi.scanNetworks(true, false);  // ✅ 返回即可，后台扫描
// 参数：async=true（异步），show_hidden=false
```

**优点**：
- ✅ 不阻塞主线程
- ✅ MQTT loop 继续运行
- ✅ 传感器采集继续进行

### **方案 2：增加 MQTT callback 超时保护**

**修改**：`src/main.cpp`

```cpp
void mqttCallback(char* topic, byte* payload, unsigned int length) {
  unsigned long callbackStart = millis();
  
  // ... 处理逻辑 ...
  
  unsigned long callbackDuration = millis() - callbackStart;
  if (callbackDuration > 1000) {  // 超过 1 秒就警告
    Serial.printf("⚠️  MQTT callback 耗时过长：%lu ms\n", callbackDuration);
  }
}
```

### **方案 3：增加 delay 到 20-50ms**

**修改**：`src/main.cpp` 的 loop 末尾

```cpp
// 原代码：
delay(10);

// 新代码：
delay(20);  // 给系统任务更多时间
```

## 🛠️ 实施修复步骤

### Step 1：修复 WiFi 异步扫描

```cpp
// src/web_server.cpp 中的 handleScanWiFi()
void WebServerManager::handleScanWiFi() {
  wifi_mode_t currentMode = WiFi.getMode();
  
  if (currentMode == WIFI_AP) {
    WiFi.mode(WIFI_AP_STA);
  }
  
  // 改为异步扫描
  int n = WiFi.scanNetworks(true, false);  // ✅ 异步模式
  String json = "[";
  
  // 实际上在 HTTP 响应时，扫描可能还没完成
  // 需要等待扫描完成
  int maxWait = 100;  // 最多等 100ms
  while (WiFi.scanComplete() < 0 && maxWait-- > 0) {
    delay(10);  // 短 delay 等待扫描结果
  }
  
  n = WiFi.scanComplete();
  
  for (int i = 0; i < n && i < 20; i++) {  // 限制最多返回 20 个网络
    if (i > 0) {
      json += ",";
    }
    json += "{\"ssid\":\"" + WiFi.SSID(i) + "\",\"rssi\":" + WiFi.RSSI(i) + "}";
  }
  
  json += "]";
  
  if (currentMode == WIFI_AP) {
    WiFi.mode(WIFI_AP);
  }
  
  sendResponse(200, "application/json", json);
}
```

### Step 2：增加 MQTT callback 保护

```cpp
// src/main.cpp 中的 mqttCallback()
void mqttCallback(char* topic, byte* payload, unsigned int length) {
  #if DEBUG_MODE
  unsigned long callbackStart = millis();
  #endif
  
  if (length > 500) {
    Serial.println("❌ 指令长度超过限制");
    return;
  }
  
  // ... 其他处理 ...
  
  #if DEBUG_MODE
  unsigned long callbackDuration = millis() - callbackStart;
  if (callbackDuration > 100) {
    Serial.printf("⚠️  MQTT callback 耗时：%lu ms\n", callbackDuration);
  }
  #endif
}
```

### Step 3：增加 loop delay

```cpp
// src/main.cpp 的 loop 末尾
void loop() {
  // ... 所有处理代码 ...
  
  // 小延迟避免看门狗重启，并给系统任务足够的 CPU 时间
  delay(20);  // 从 10ms 增加到 20ms
}
```

## 💡 为什么之前没有发现这个问题？

1. **WiFi.scanNetworks() 只在用户点击时触发**
   - 不是持续发生
   - 取决于用户是否在网页上点击"扫描 WiFi"按钮
   - 如果没有点击过，就不会发现问题

2. **主 loop 中没有超时检测**
   - 没有记录 loop 执行时间
   - 没有警告日志
   - 用户只能看到"卡死"现象，不知道原因

3. **这是常见的 WiFi 库问题**
   - ESP32 WiFi 库的 scanNetworks() 设计就是阻塞式的
   - 官方文档没有明确警告这一点
   - 很多项目都踩过这个坑

2. ✅ 增加 MQTT callback 保护
3. ✅ 优化 loop delay

**预期效果**：

- ✅ MQTT 持续上报
