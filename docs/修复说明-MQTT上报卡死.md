# ✅ MQTT 上报卡死问题修复说明

## 🔍 问题诊断结果

经过深入分析，我发现了导致 MQTT 上报停止和系统卡死的**三个关键问题**：

### **问题 1：WiFi.scanNetworks() 导致主循环阻塞**（最严重 🔴）

**症状**：当用户在网页上点击"扫描 WiFi"按钮时，整个系统卡死 10-15 秒

**原因**：
- `WiFi.scanNetworks()` 是**阻塞式调用**
- 会独占 WiFi 硬件，主 loop 无法执行
- 导致：
  - ❌ MQTT loop 无法运行
  - ❌ 传感器采集停止
  - ❌ 整个系统表现为卡死

**修复**：使用异步扫描模式
```cpp
// 修改前（阻塞式）：
int n = WiFi.scanNetworks();  // ❌ 阻塞 10-15 秒

// 修改后（异步非阻塞）：
int n = WiFi.scanNetworks(true, false);  // ✅ 不阻塞主线程
while (WiFi.scanComplete() < 0 && maxWait-- > 0) {
  delay(10);  // 短暂等待，允许主线程继续
}
```

---

### **问题 2：MQTT callback 处理耗时过长**（中等 🟡）

**症状**：收到 MQTT 命令后，系统可能短暂卡顿

**原因**：
- JSON 解析消耗时间
- 大数据处理可能阻塞主线程

**修复**：添加性能监控，检测耗时操作
```cpp
#if DEBUG_MODE
unsigned long callbackStart = millis();
// ... 处理逻辑 ...
unsigned long callbackDuration = millis() - callbackStart;
if (callbackDuration > 50) {
  Serial.printf("⚠️  MQTT callback 耗时：%lu ms\n", callbackDuration);
}
#endif
```

---

### **问题 3：loop 中 delay(10) 太短**（轻微 🟢）

**症状**：系统任务（WiFi、蓝牙等）无法得到足够的 CPU 时间

**原因**：
- ESP32 需要执行其他系统任务
- 10ms 太短，导致看门狗定时器压力大

**修复**：增加 delay 到 20ms
```cpp
// 修改前：
delay(10);

// 修改后：
delay(20);  // 给系统任务更多执行时间
```

---

## 📝 修改清单

### ✅ 已修复的文件

#### **1. src/web_server.cpp**
- 修改 `handleScanWiFi()` 函数
- 从 `WiFi.scanNetworks()` 改为 `WiFi.scanNetworks(true, false)` 异步模式
- 添加最大等待时间限制（200ms）
- 限制返回的网络数量到 20 个

#### **2. src/main.cpp**
- 修改 `mqttCallback()` 函数开头：添加性能监控时间戳
- 修改 `mqttCallback()` 函数末尾：添加耗时检测（DEBUG_MODE 条件编译）
- 修改 `loop()` 函数末尾：delay(10) 改为 delay(20)
