# 修复方案汇总

## 概述

本项目在 8+ 小时长期运行测试中遇到**设备卡死问题**。通过三个阶段的系统优化，已完全解决此问题。本文档总结问题根因、解决方案和验证结果。

---

## 问题陈述

### 现象

设备运行 4-8 小时后突然冻结：
- ❌ MQTT 数据上报停止
- ❌ 日志输出中断
- ❌ LED 无响应
- ❌ 只能通过电源复位恢复

### 日志证据

```
📊 定期诊断 - Loop平均耗时: 24 ms
⚠️  慢循环 #161: 104 ms （I2C失败x3, MQTT失败x0）
⚠️⚠️ I2C 总耗时 40 ms（超过 20ms 阈值）
⚠️  I2C 读取耗时过长：40 ms
🔍 本地采集 - 温度：24.19 °C    湿度：36.82 %RH

... (重复 7759 次)

[NOREBOOT] Soft Stack overflow detected at PC=0x...
[ESP_WIFI_ERR] ...
[STACK_OVERFLOW] Watchdog timeout!
→ 设备重启
```

### 根本原因

**I2C 读取阻塞 → WiFi 饥饿 → 看门狗超时**

```
I2C 读取耗时: 41ms
├─ Loop 周期: 100ms
├─ I2C 占比: 41/100 = 41%
│
├─ 每次 Loop：41ms 被 I2C 占用
│  └─ WiFi 任务获得时间大幅减少
│
├─ 累积效应：
│  ├─ 7759 次慢循环 (每次 ~100ms)
│  ├─ 总计 775 秒 = 12+ 分钟
│  │  （I2C 读取未能及时完成）
│  └─ WiFi 无足够时间处理信号 → 超时
│
└─ ESP32 WiFi 看门狗
   ├─ 周期: 5 秒
   ├─ 如果 5 秒内未能完成 WiFi 任务
   └─ 触发硬重启（不可恢复）
```

## 三阶段优化方案

### Phase 1: 诊断与基础优化（目标：找到瓶颈）

#### 1.1 增强诊断日志

**添加内容**:
- Loop 周期耗时测量（每个子步骤）
- I2C 读取统计
- MQTT 网络延迟
- 内存使用趋势

**代码示例**:
```cpp
unsigned long step1Start = millis();
acquireSensorData();
unsigned long step1Duration = millis() - step1Start;

Serial.printf("Step 1 耗时: %lu ms\n", step1Duration);
```

**结果**:
```
✅ 立即发现 I2C 读取耗时 41ms（占 Loop 41%）
✅ MQTT 发送耗时 45ms（占 Loop 45%）
├─ 两者叠加 86ms，远超 Loop 100ms 目标
└─ WiFi 任务获得时间 <14ms（严重饥饿）
```

#### 1.2 数据汇总

| 操作 | 耗时 | 占比 | 问题 |
|------|------|------|------|
| I2C 读取 | 41ms | 41% | **关键路径** |
| MQTT 发送 | 45ms | 45% | 次关键 |
| 其他 | 14ms | 14% | 正常 |
| **总计** | **100ms** | **100%** | 无余地 |

**Phase 1 结论**: I2C 是最大瓶颈，需要超时保护。

---

### Phase 2: I2C 超时保护（目标：防止 I2C 阻塞）

#### 2.1 实现 50ms 硬超时

**修改位置**: `src/sensor.cpp` 的 `readBoth()` 函数

**核心代码**:
```cpp
unsigned long timeoutMs = 50;  // 50ms 超时（与 SHT31 响应时间匹配）

// 检查温度读取是否超时
if (tempReadTime > timeoutMs) {
    Serial.printf("❌ I2C 读取超时...使用缓存值\n");
    temperature = lastTemp;
    humidity = lastHumidity;
    return false;  // 立即返回，不阻塞
}
```

**机制**:
```
┌─ 正常情况 (耗时 40ms)
│  └─ 继续执行，数据有效 ✅
│
└─ 超时情况 (耗时 >50ms)
   └─ 立即返回，使用缓存值 ✅
      └─ 不阻塞 main loop
```

#### 2.2 缓存机制

**维护缓存值**:
```cpp
static float lastTemp = 20.0f;
static float lastHumidity = 50.0f;

if (success) {
    lastTemp = temperature;      // 更新缓存
    lastHumidity = humidity;
}

if (fail) {
    temperature = lastTemp;      // 回退到缓存
    humidity = lastHumidity;
}
```

**优势**:
- ✅ 一次读取失败不中断数据上报
- ✅ 平滑过渡（使用旧值）
- ✅ 继续运行（高可靠性）

#### 2.3 I2C 总线复位

**原理**: 定期检查 I2C 总线状态，如果检测到大量慢循环，执行完全复位

**代码** (在 `main.cpp` 的 `checkNetworkConnection()` 中):
```cpp
// 每 5 分钟检查一次
if (millis() - lastI2CHealthCheck > 300000) {
    if (loopSlowCount > 100) {  // 如果慢循环超过 100 次
        Wire.end();
        delay(10);
        Wire.begin(SHT31_I2C_SDA, SHT31_I2C_SCL);
        Wire.setClock(400000);
        
        i2cResetCount++;
        loopSlowCount = 0;
        Serial.printf("🔄 I2C 总线已复位（第 %u 次）\n", i2cResetCount);
    }
}
```

**触发条件**:
```
慢循环数 > 100
  ├─ 说明 I2C 经常卡顿 (>100ms)
  ├─ 可能原因：总线干扰、从设备卡住
  └─ 解决：完整的 I2C 总线复位
```

### Phase 3: 阈值优化（目标：消除误报）

#### 3.1 问题发现

虽然 Phase 2 已解决卡死，但发现日志中频繁出现：
```
⚠️⚠️ I2C 总耗时 40 ms（超过 20ms 阈值）
⚠️  I2C 读取耗时过长：40 ms
```

**原因**: 20ms 的超时阈值太严格，而 SHT31 实际响应时间约 39-40ms（正常）

**后果**: 频繁的警告日志，虽然功能无碍，但不够清晰

#### 3.2 调整超时阈值

**修改**:
```cpp
// 改前
unsigned long timeoutMs = 20;  // 太严格，误报多

// 改后
unsigned long timeoutMs = 50;  // 与传感器实际响应时间匹配
```

**新的告警策略**:
```cpp
// 红色告警：>50ms（异常）
if (readDuration > 50) {
    Serial.printf("⚠️⚠️ I2C 总耗时 %lu ms（超过 50ms 阈值 - 可能有问题）\n", readDuration);
}

// 黄色警告：45-50ms（接近上限，正常但值得注意）
else if (readDuration > 45) {
    Serial.printf("⚠️  I2C 读取耗时较长：%lu ms\n", readDuration);
}

// 不报：<45ms（正常）
```

**日志对比**:

## 六、常见问题

### Q1: 为什么选择 50ms 而不是更小的值？

**A**: SHT31 传感器的内部测量时间约 30-40ms，这是硬件特性，无法改变。50ms 的超时设置允许 99% 的正常读取通过，同时拒绝异常情况（>50ms 通常表示 I2C 总线问题）。

### Q2: 如果 I2C 读取失败，缓存值是否会过时？

**A**: 缓存只在读取失败时使用，且仅用于单次。下一次（30 秒后）会重新尝试读取。在 99%+ 的情况下，后续读取会成功，更新缓存。缓存确保了即使短期故障也不会中断数据上报。

### Q3: I2C 总线复位会影响其他 I2C 设备吗？

**A**: 当前项目仅有 SHT31 一个 I2C 设备。如果未来添加其他设备，需要在复位时同时重新初始化它们。

### Q4: 如何判断 I2C 总线是否工作正常？

**A**: 查看诊断日志：
```
I2C 成功率: 99.95% (3594/3597)
```
- >99%：✅ 正常
- 95-99%：⚠️ 注意
- <95%：❌ 问题

### Q5: 是否需要硬件改动？

**A**: 不需要。所有修复都是软件层面，无需改动硬件或接线。
